# #15 오류 번호와 서버 진단 기록

대상 이슈: https://github.com/yazxyng/FeynLoop/issues/15

## 동작

인증·계정 설정·자료·학습 API 요청마다 서버에서 UUID v4를 생성합니다. 실패 응답의 `requestId`, `X-Request-ID` 헤더, 서버 오류 로그에 같은 번호를 사용합니다. 성공 응답에는 헤더만 추가하고 실패 로그는 남기지 않습니다. 호출자가 보낸 요청 번호는 사용하지 않습니다.

사용자는 기존 오류 안내의 **오류 번호 보기**를 펼쳐 번호를 선택·복사할 수 있습니다. 로그인, 채팅, 등록, 계정 설정 및 자료 조회 실패 안내에 전달합니다. 새 작업·화면 이동·안내 닫기 시 이전 오류와 번호를 함께 지웁니다. 성공 알림에는 번호를 표시하지 않습니다.

번호가 전달되면 호스팅 서비스의 함수 로그에서 해당 UUID를 검색합니다. 로그의 `route`는 실제 URL 대신 고정된 API 종류이고, `stage`는 인증·입력 검증·PDF 추출·AI 분석·저장 등 고정된 단계입니다. `durationMs`는 앱의 API 처리 시작부터 실패 응답을 만드는 시점까지의 시간입니다.

## 기록하는 값

- `requestId`: 서버에서 생성한 임의 번호
- `route`: 고정된 API 종류
- `stage`: 고정된 처리 단계
- `status`: HTTP 상태 코드
- `durationMs`: 처리 시간
- `code`: 있는 경우에만 표준 PostgreSQL/PostgREST 오류 코드

오류 메시지 원문, stack, 전체 URL·쿼리, 요청 헤더·쿠키·본문, 계정 아이디, 비밀번호, 복구코드, API 키, 문서 원문, 사용자 답변은 이 진단 로그에 기록하지 않습니다. 여러 요청이 동시에 처리되어도 Node.js AsyncLocalStorage로 번호와 단계를 분리합니다. 기존의 비밀 없는 스키마 검증·대체 질문 로그는 유지합니다.

## 수정 위치

- 요청별 문맥과 로그 필드: `src/lib/server/diagnostics.ts`
- API 응답과 오류 번호 연결: `src/lib/server/http.ts`
- 클라이언트의 번호 검증·전달: `src/lib/request-error.ts`
- 기존 안내 안의 번호 표시: `src/components/inline-feedback.tsx`
- API별 세부 단계: 각 route 파일과 인증·분석·저장 함수의 `setDiagnosticStage`

## 검증

- 실패 응답 본문·헤더·서버 로그의 번호 일치
- 병렬 요청의 번호·실패 단계 분리
- 민감한 문자열·예외 stack·사용자가 보낸 번호의 로그 유입 차단
- 정상 응답의 기존 본문·상태 코드·쿠키 유지
- 학습·계정·로그인 요청 도우미의 오류 번호 전달
- JSON이 아닌 응답도 유효한 헤더 번호를 보존
- 번호 없는 네트워크 실패에는 임의 번호를 만들지 않음
- 기존 오류 안내에서 펼치기 및 작은 화면 표시
- 빌드된 서버의 입력 오류 응답 번호·PDF 업로드 확인

실제 사용자 데이터나 외부 AI를 사용하지 않고 로컬 임시 서버와 모의 응답으로 검증했습니다. 새 SQL·외부 로그 서비스·API 키 설정은 필요하지 않습니다. GitHub push·PR 생성·배포는 별도 단계입니다.

## 범위

앱이 처리한 API 오류를 추적합니다. 앱 실행 전의 플랫폼 장애·연결 실패·프록시 응답에는 번호가 없을 수 있으며, 이 경우 존재하지 않는 서버 로그에 연결되는 것처럼 번호를 만들지 않습니다. 전체 플랫폼 모니터링이나 사용자 동작 수집 기능은 추가하지 않습니다.
